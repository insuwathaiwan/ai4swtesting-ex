# Activity 1 – Step 2: A specific prompt with context

**Chatbot / model:** <!-- e.g., ChatGPT (GPT-5), Gemini, Claude / เช่น ChatGPT (GPT-5), Gemini, Claude -->

## Prompt

```text
Act as a professional software tester and suggest test ideas for the feature delimited by three hashes. All test ideas should be focused on discovering risks that impact the quality characteristics: Functionality, Data Integrity and Security
###
* As a paralegal, in order to store and share legal documents, I want to be able to securely upload documents.
* Acceptance criteria:
  - Upload should support the following common file formats: PDF, DOCX, TXT
  - The maximum file size should be 20MB
  - When a document is uploaded it should give a progress update to the user
  - Once uploaded, the document must initially be only accessible to the person who has uploaded it
  - A report of the upload and whether it was successful or not will be stored in the auditing feature
###
```

## Response

Test Ideas: Secure Document Upload
Functionality

File formats

Upload valid PDF, DOCX and TXT files, each opens correctly after download.
Upload unsupported formats (.exe, .jpg, .xlsx, .doc, .rtf, .zip) and confirm a clear rejection message.
Upload files with uppercase or mixed-case extensions (.PDF, .DocX).
Upload files with no extension, double extensions (contract.pdf.exe) and trailing spaces or dots.
Upload an empty (0 KB) file of each format.
Try password-protected PDFs, DOCX files with macros, and PDFs with embedded attachments.

File size (20MB limit)

Test boundaries: 19.99MB, exactly 20MB, 20MB + 1 byte, and 100MB+.
Check whether “20MB” is treated as 20×1000×1000 or 20×1024×1024 bytes, and that the UI, API and docs agree.
Confirm the size limit is enforced on the server, not just in the client.
Check that an oversized upload is rejected early rather than after the whole file has transferred.

Progress indicator

Progress advances monotonically from 0% to 100% for large files.
Very small files still show feedback rather than flashing.
Progress is accurate on slow or throttled networks.
Cancel mid-upload: progress stops, no partial file is stored, the audit entry reflects cancellation.
Network drop mid-upload: the user sees an error and no corrupted file is left behind.
Refresh, close the tab or navigate away mid-upload.
Progress stays correct with multiple simultaneous uploads.

General behavior

Same file uploaded twice, and two different files with the same name.
File names with spaces, unicode, emoji, very long names (255+ chars) and special characters (& % # ' ").
Upload from different browsers, devices and OS combinations.
Concurrent uploads by many users (load and race conditions).
Retry after a failed upload works without duplicates.
Data Integrity
Compare checksums (SHA-256) of the original and the downloaded file for every format.
Confirm no truncation or corruption for files at and near the 20MB limit.
Unicode and special characters in TXT files survive intact (UTF-8, UTF-16, other encodings, BOM, line endings).
File metadata (name, size, timestamp, uploader ID, MIME type) is stored correctly.
Interrupted uploads (network loss, server restart, browser crash) leave no orphaned or partial files or database records.
Storage and database stay consistent: no record without a file, and no file without a record.
Two users uploading simultaneously with identical names do not overwrite each other.
Retried uploads and double-clicks on the upload button do not create duplicate records.
Behavior when storage is full or the storage service is unavailable: a clear error, no false success.
Uploaded content is never altered, re-encoded or stripped by the system, unless that is documented.
Backup and restore preserves documents together with their owner and access settings.
Audit report integrity:
Every attempt (success, failure, cancel, rejected type or size) produces exactly one audit entry.
Entries contain correct user, timestamp, file name, size and outcome.
Audit status matches the real state (no “success” logged when the file is missing, or the reverse).
Audit entries cannot be edited or deleted by the uploader.
An audit entry is still written if the audit service is down (queued, or the upload is blocked, whichever the requirements specify).
Timestamps are consistent across time zones and server clock changes.
Security

Access control

After upload, only the uploader can view, download, list or search the document.
A different logged-in user cannot access the document by guessing or incrementing IDs or URLs (IDOR).
An unauthenticated user cannot upload, download or list documents.
Access is denied after logout or session expiry, including via direct links.
Revoked or deactivated users lose access immediately.
Admin and privileged access: is it allowed, and is it logged?
API endpoints enforce the same permissions as the UI (test with Postman or curl, no UI).
Download links: are they guessable, do they expire, and can they be shared without authentication?

Malicious file handling

Upload files containing malware (EICAR test file) and confirm they are scanned and blocked.
Upload files whose extension does not match their content (an .exe renamed .pdf) and confirm validation by content, not just extension or MIME header.
Upload PDFs with embedded JavaScript, and DOCX files with macros or external links.
Upload zip bombs or decompression bombs disguised as DOCX (DOCX is a zip container).
Upload TXT or DOCX containing script tags, HTML or SQL fragments, and confirm they are never executed or rendered unsafely when displayed or previewed.
XXE and XML-based attacks inside DOCX files.

Injection and path attacks

File names containing path traversal (../../etc/passwd, ..\..\) and null bytes (file.pdf%00.exe).
File names containing XSS payloads (<script>alert(1)</script>.pdf) and SQL injection strings, checking where the name is displayed (UI, audit log, emails).
Tampered requests: modified Content-Type, Content-Length, file size and filename headers.
CSRF on the upload endpoint.
Server-side request forgery or command injection through metadata fields.

Data protection

Transport uses HTTPS only, and HTTP uploads are refused or redirected.
Documents are encrypted at rest, and storage buckets or folders are not publicly accessible.
Uploaded files are not served from a path that allows direct, unauthenticated access.
Documents are served with safe headers (Content-Disposition, X-Content-Type-Options: nosniff) so they cannot execute in the browser.
File contents and personal data do not leak into logs, error messages, URLs or the audit report.
Error messages do not expose server paths, stack traces or storage details.
Rate limiting and abuse protection: repeated uploads, large-volume uploads and denial-of-service via many 20MB files.
Session handling: uploads cannot continue or be hijacked after session expiry or token theft.
Metadata in uploaded files (author, location, hidden text) is handled according to policy.
Highest-Priority Risks to Test First
Unauthorized access to another user’s document (IDOR and API bypass).
Server-side file type and size validation bypass.
Malicious file content (malware, macros, traversal in filenames).
Corrupted or partial files and false “success” results.
Missing or inaccurate audit entries.
